# A｜GPTS 迁移与迭代

## 方案门禁：按顺序完成

1. **逐份读取源材料**：建立台账，列出 GPTS 名称、Instructions、启动 Prompt、Knowledge 每份文件、Actions、Capabilities、设置、历史输出、成功与失败反馈的来源、版本、用途、读取状态。引用具体文件与段落；缺失或受阻时注明，不能把未知材料写成已审计。
2. **还原旧能力并重构目标业务链**：从触发、输入、判断、资料读取、工具执行、生成、审核到交付，还原旧链和失败点。先写清目标用户、任务、输入输出、成功标准、异常和人工决策点，再规划目标链。将旧反馈映射到新链节点与验收案例；此时不预定 Skill 数量或仓库。
3. **逐段去重、查冲突并核实事实**：对每条规则或 Knowledge 片段标注保留、合并、改写、归档、删除，记录来源、依据和唯一目标位置。处理重复模板、矛盾版本、过时工具/模型、未执行指令与缺失依赖。平台规则等易变主张核查官方来源；小红书推荐机制的第三方经验只能标为假设，不能当作已证实算法。
4. **决定资产去向**：先判断 Skill 应完成哪些任务，再按用途把执行协议放 SKILL.md、短小稳定规则放 references/、模板放 assets/、确定性程序放 scripts/。仅当体量、更新频率、跨 Skill 共享或权限需求确有依据时采用 GitHub；若采用，给出路径、Manifest、固定版本、权限、实际读取方式和失败行为。保留来源记录，避免两处重复维护正文。
5. **筛选开源候选，再决定复用**：按任务检索官方规范与 GitHub 原始项目。逐项核查许可证、核心文件、功能适配、依赖、维护情况、目标环境和可替换模块；标注直接采用、合规二改、仅借鉴或不采用的理由。没有明确许可不复制代码或资料；封面项目可以提供排版方法，不能证明平台推荐算法。
6. **比较架构并推荐**：至少比较单 Skill 多模式、按能力拆成多个 Skill、必要时 Skill＋外部工具；从触发冲突、共享资产、依赖、维护成本和旧能力保留评价。两组上传材料不能直接推定两个 Skill。交付旧链和推荐目标链图、能力兼容矩阵、目标文件树、逐文件迁移清单、按需资产路由与测试矩阵；说明未选方案的取舍。
7. **提交核实**：交付证据台账、去重与事实状态、开源候选筛选、架构比较、推荐方案、逐文件计划和验收用例。明确需要用户决定的架构、共享范围及重大行为变化；用户核实前不构建目标 Skill、不写入目标资产库。

材料不齐时完成可独立核实的部分，列出受阻结论和补充资料；不要用默认假设越过方案门禁。包外方案模板为 `templates/A-migration-plan.md`，仅在实际使用时按资产路由规范取回。

## 确认后的构建与验证

按已核实的方案制作目标 Skill，写清触发、输入、判断、资源读取、执行、输出、QA 与停止条件；只迁移有依据且必要的资产。若采用仓库，验证 Manifest 固定版本、权限、摘要与实际读取；若无需仓库，目标 Skill 独立使用随包 references、assets 和 scripts。

运行静态校验、正反触发、代表性任务、资料精确命中和缺失场景、旧成功案例及失败案例回归。记录通过、失败、受阻、未运行；本地结构检查不等于安装或真实业务运行，目标包和远端资产各自核验。
